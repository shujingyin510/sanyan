# Agent 成熟度 / 可信度加固计划

> 目标：不加新功能，把现有 agent 的能力「压实」——让每个头条数字可一键复现、
> 让活跃执行路径清晰、让 dogfooding 落地或讲清。
> 适用范围：`agent_system/`、`ternary_engine.py`、相关 `docs/research/` 与 README 的 agent 部分。

---

## 0. 诊断（基于当前仓库的实测）

先纠正一个常见误判：**agent 的单测并不薄**。
`test_agent_v5.py`(158 个测试函数) + `test_agent.py`(31) + `test_agent_runtime.py`(39)
+ `test_agent_safety.py`(故障注入框架) ≈ 228+ 项。所以「补单测」不是重点。

真正影响可信度的是下面四条：

| # | 短板 | 证据 |
|---|------|------|
| A | **头条数字散落且互相对不上** | 越界改善：ROADMAP 写 `-11.5%`，`agent_benchmark_report.md` 写 `-16.7%`(50→33.3)。同一指标两个值。 |
| B | **部分数字无复现路径 / 可能属于已拆出的 UR 仓库** | README 因果链 `40.9%→82.5%→84.5%` 未标复现命令；ROADMAP 的盲评 `79.7%`、`p=0.0287` 属 UR/门控，已独立成新仓库却仍留在此处。 |
| C | **测试验证「骨架能跑」，不验证「结论成立」** | 228 项多是 API/行为测试；没有一个固定随机种子、断言效应方向/阈值的复现测试层。 |
| D | **半 dogfooding** | `decision.san` 注释自陈「Python 版已迁移到 ternary_engine.py，本文件保留作参考」——活跃路径是 Python，三言版只是展示。 |

> 一句话：agent 是「骨架全、能跑、但结论靠文档声明撑着」。加固＝把声明变成可复现的事实。

---

## 阶段 0 — 结论清账（约半天，**先做，性价比最高**）

把所有量化声明拉一张总表，立刻看清「多少是真的」。

**动作**
1. grep 全仓 README / README_EN / ROADMAP / `docs/research/*.md` 里每一处百分比、p 值、样本数。
2. 对每条声明填：来源文档 → 产生它的模块/脚本 → 是否可复现(是/否/已迁移到 UR 仓库) → 是否与他处冲突。
3. 跑一遍现有复现命令 `sanyan bench --type safety`、`--type honesty`，确认还能跑、输出是否对得上报告里的数。

**交付**：`docs/CLAIMS.md`（声明清账表）。
**完成判据**：每个数字都能归到「可复现 / 待补 / 已迁移 / 作废」四类之一；A、B 两条里的冲突点全部列出。

---

## 阶段 1 — 让每个存活的声明可一键复现（约 2–3 天）

**动作**
1. 每条保留的声明配一条**单命令复现**：固定随机种子，跑完写出 `results/<claim>.json`（含日期、种子、git commit）。
2. 文档不再写「裸数字」，改为引用 `results/` 里的工件 + 生成命令 + commit。
3. 处理冲突与归属：
   - 越界 `-11.5%` vs `-16.7%`：重跑一次定一个真值，另一处改掉。
   - 盲评 / p 值等 UR 内容：从本仓 ROADMAP 移除或改为「见 UR 仓库」链接，不在此处复述。
   - 跑不出来、又没数据的：标 `作废` 并从文档删除。

**交付**：`results/` 目录 + 更新后的各文档引用。
**完成判据**：`docs/CLAIMS.md` 里「可复现」那一类，每条都能 `运行命令 → 得到与文档一致的工件`。

---

## 阶段 2 — 复现测试层进 CI（约 2–3 天）

把「结论成立」也变成会失败的测试，防止文档悄悄漂移。

**动作**
1. 新建 `tests/repro/`：每个核心结论一个缩小规模、固定种子的复现测试。
2. **断言效应方向/阈值，不断言精确浮点**。示例：
   - 安全检出 ≥ 95%（报告称 100%）；
   - 校准后越界率 比基线低 ≥ 10 个百分点；
   - 校准 ECE 校准后 < 基线。
3. 接入 CI（README 已有 CI 徽章）。任一结论复现破裂 → CI 红 → 文档无法和代码脱节。

**交付**：`tests/repro/` + CI 配置更新。
**完成判据**：CI 绿；手动改坏 `ternary_engine.py` 的门控阈值能让对应 repro 测试变红。

---

## 阶段 3 — dogfooding：落地或讲清（约 1–2 天，二选一）

**选项 A（理想）**：让 `decision.san` 成为真实路径。
- 通过 VM 跑三言版决策核心（接受比 Python 慢）；
- 加一个**奇偶校验测试**：同一批输入下 `decision.san` 与 `ternary_engine.py` 判定一致。
- 价值：把「语言强到能跑自己的 agent」变成硬证据。

**选项 B（保底）**：如果 A 暂不可行，就在 README + 所有相关文档明确写：
活跃引擎是 `ternary_engine.py`(Python)，三言版是能力演示。**不留模糊**。

**完成判据**：读者不会再误以为 agent 是纯三言自举；要么有 parity 测试，要么有明确声明。

---

## 阶段 4 — 活跃路径地图 + README 诚实化（约 1 天）

**动作**
1. 给 `agent_system/` 的 ~40 个模块标注：**活跃路径 / 实验性 / 已弃用**（一张表或一张图）。
2. 重写 README 的 agent 段落，使每条能力的措辞与阶段 1 的复现状态一致——可复现的正常讲，未复现的标「实验性」，不再用「做不到」「100%」这类未经工件支撑的措辞。

**交付**：`agent_system/README.md` 增加路径地图；README agent 段落改写。
**完成判据**：随机翻 README 里任一 agent 数字，都能在 `results/` 找到对应工件。

---

## 阶段 5 — 方法学透明（持续）

针对人工盲评、统计显著性这类声明：提交原始评分表、题库 prompt、逐题打分、分析脚本，
让读者能从提交的数据**自己重算 p 值**。没有原始数据的统计结论一律降级为「初步观察」。

---

## 排期与优先级

```
阶段0 清账(0.5d) ─→ 阶段1 复现(2-3d) ─→ 阶段2 CI(2-3d)
                          │
                          ├─→ 阶段3 dogfooding(1-2d)  ← 可与阶段2并行
                          └─→ 阶段4 路径地图+README(1d)
阶段5 方法学透明：贯穿，随阶段1一起做
```

总量约 1.5–2 周（单人）。**阶段 0 半天就能让你知道「现在到底有多少是真的」**，建议立刻做。

## 明确不做的事

- 不加新层、新工具、新集成——成熟度阶段不扩面积。
- 不为了好看调高数字——重跑得到什么就是什么，方向对、可复现，比数字大更值钱。
- 不动语言侧（它已经更成熟）——这份计划只压实 agent。
